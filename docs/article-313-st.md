# 我用 313 家 ST 公司验证财务排雷规则，结果把最初的设计全推翻了

> 一个关于「直觉为什么不可靠」的故事，附完整可复现的实验代码。

---

## 起因

A 股散户最大的恐惧不是买贵了，是踩雷。

财报看着漂亮、股价一路涨，突然某天公告「前期会计差错更正」，几百亿资产凭空消失。康美药业、康得新、獐子岛……每隔几年就来一次。

我就想做一个工具：**输入股票代码，用财务数据把有问题的公司筛出来。**

规则怎么定？凭直觉，规则应该很直白：

1. 利润是观点，现金流是事实 → **经营现金流长期低于净利润**的公司有问题
2. 商誉是纸面资产 → **商誉占净资产过高**的有减值风险
3. 一边趴着大量现金一边大量借债 → **存贷双高**很可疑
4. 资不抵债 → **净资产为负**

听起来很合理对吧？第一条尤其合理——几乎所有讲财务分析的文章都在强调「净利润和经营现金流的背离」。

我先写了代码，跑通了。然后做了一个决定：**不凭直觉判断规则有没有用，用数据验证。**

---

## 第一步：找验证集

要验证「规则能不能识别有问题的公司」，得先有一批「已知有问题」的公司。

最天然的验证集是 **ST / *ST 股票**——这些是交易所已经认定的风险警示公司。

我从公开接口拉了全市场数据：

| 项目 | 数量 |
| --- | --- |
| A 股总数 | 5,563 家 |
| ST / *ST | **313 家** |
| 有效样本（有 2025 年报数据） | ST 261 家 / 正常 5,035 家 |

验证逻辑很简单：**如果规则有效，它标红 ST 公司的比例应该显著高于标红正常公司的比例。**

我定义一个指标叫「提升倍数」：

```
提升倍数 = ST 公司触发率 ÷ 正常公司触发率
```

1.0x 等于随机猜测，越高越有区分力。

---

## 第二步：结果把我的直觉打穿了

逐条规则跑下来：

| 规则 | ST 命中率 | 正常公司误报率 | 提升倍数 |
| --- | --- | --- | --- |
| 净资产为负 | 28.0% | 0.8% | **37.14x** |
| 连续三年亏损 | 39.7% | 10.2% | 3.87x |
| 连续两年亏损 | 49.8% | 16.9% | 2.95x |
| 经营现金流连负 | 20.2% | 8.3% | 2.43x |
| 高商誉 > 50% | 2.3% | 1.0% | 2.45x |
| **净利现价比 < 0.3** | **1.2%** | **7.5%** | **0.16x** |

看最后一行。

**「净利现价比」的提升倍数是 0.16x —— 它是反指标。**

意思是：ST 公司触发这条规则的概率，比正常公司**还低 84%**。如果不做验证直接上线，这条我最有信心的规则，会系统性地把正常公司标红、把真正有问题的公司漏掉。

---

## 第三步：为什么会反着来

我盯着这个数字想了很久，最后查数据才看明白。

「净利现价比」= 累计经营现金流 ÷ 累计净利润。代码里我写了一个保护：

```ts
if (profit <= 0) return null;  // 亏损公司跳过，比值无意义
```

问题就在这里。

**ST 公司绝大多数处于亏损状态。** 净利润为负时，这条规则直接跳过——不是不报，是根本没参与判断。

而留下的样本是什么？是「有盈利但现金流差」的公司。这类公司里当然也有问题企业，但更多是**成长期公司**：收入在扩张，应收账款和存货同步堆积，经营现金流自然跟不上净利润。这是正常的商业现象，不是造假。

所以这条规则实际上变成了「成长期探测器」，而不是「风险探测器」。

**更深的错误在于：我把两个不同的目标混为一谈了。**

| 我想预测的 | 实际做出来的 |
| --- | --- |
| 财务造假（利润是假的） | 财务恶化（利润是真的但很差） |
| 验证集：已知造假案例，样本极少 | 验证集：ST 公司，样本充足 |

ST 标签的主要成因是**持续亏损、净资产为负、审计非标**，而不是「造假被查出来」。用 ST 做验证集，只能验证前者，不能验证后者。

**用 A 的验证集去否定 B 的规则，逻辑上根本不成立。** 我差点把这个当成「规则无效」的证据把整个项目废掉。

---

## 第四步：重新设计

既然验证集是 ST，那就老老实实做**风险警示预测**：

把所有规则按提升倍数排序，只保留真正有区分力的。然后遇到第二个问题——**精确率和召回率不可兼得**：

| 组合 | ST 命中 | 正常公司误报 | 标记家数 |
| --- | --- | --- | --- |
| 仅「净资产为负」 | 27.6% | **0.8%** | 40 家 |
| 净资产为负 + 连续亏损 | 63.6% | 17.7% | 893 家 |
| 全部规则都加上 | 73.9% | **39.0%** | 1,964 家 |

最后一行是关键：**规则越多，召回越高，但会标出 39% 的 A 股。**

一个标了 1,964 家「有问题」的清单，等于没标。用户不会看第二眼。

所以最终产品不是给一个总分，也不是给一个长清单，而是**分层**：

```
[红] 高危    净资产为负 —— 34.72x 提升，全市场 112 家
[黄] 关注    连续亏损 / 现金流连负 / 高商誉 —— 约 1200 家
[绿] 未见异常
```

红灯少而准（用户不会被噪音淹没），黄灯保留覆盖面（需要时能深挖）。

> 说明：「仅净资产为负」那行统计的 40 家是**正常公司**（非 ST）中满足条件的；加上 ST 公司后，全市场红灯实际是 112 家。

---

## 第五步：工程上踩的坑

规则设计完了，还得让它跑得动。

**坑 1：逐个股票抓数据太慢**

5,563 家 × 3 张报表 = 16,689 次请求。按每秒 2 次算要两个多小时。

后来发现公开接口支持**按报告期批量返回全市场数据**——一次请求拿 500 条，5000 家只要几十个请求。全市场扫描从「两小时」降到 **48 秒**。

**坑 2：分页失败被静默忽略**

这是最危险的一个。第一版重试逻辑长这样：

```ts
let json: any = null;
for (let attempt = 0; attempt < 3; attempt++) {
  try {
    json = JSON.parse(await httpRequest(url));
    break;
  } catch {
    await new Promise((r) => setTimeout(r, 600 * (attempt + 1)));
  }
}
// 三次都失败时 json 仍是 null
const data: any[] = json?.result?.data ?? [];   // 静默变成空数组
```

后果是：**同一份数据，两次扫描跑出不同的红灯数**（112 和 108）。

金融工具最致命的缺陷就是「不可复现」。用户今天看到 112 家，明天看到 108 家，永远不会信任这个数字。

改成重试耗尽就抛异常之后，结果稳定了。

**坑 3：股票列表实时抓取也在破坏可复现性**

股票列表（含 ST 标记）每次实时请求，成分股会变动。把它也纳入缓存后，三次连跑结果完全一致。

---

## 最后：这个工具不能做什么

我觉得这部分比功能列表更重要，所以完整写在 README 里：

**不能识别财务造假。** 造假需要的信号——跨期调节、虚构海外收入、关联交易非关联化——靠比率分析基本无效。而且**缺乏有效的统计验证方法**：已知造假案例就那么几个，凑不成验证集。

**不能预测爆雷。** 我做的是「当前财务状态 × 当前 ST 状态」的横截面区分度，不是时序预警。真正的预警验证需要「事发前原始披露数据」——但已处罚公司的历史报表都被追溯重述过，公开接口拿到的是重述后的数字，还原不出原始披露的样子。

**数据有滞后。** 只用定期报告，季报披露滞后一个月以上。

这几条我写在 README 的显眼位置。因为一个工具如果不知道自己不能做什么，用户就会用它去做它做不到的事，然后怪它不准。

---

## 复盘

整个项目最有价值的产出，不是那套规则，而是这条经验：

> **优化的目标必须和验证的方法对齐。**

我想优化「造假识别」，却用「ST 预测」的验证集去评估，得到的结论必然失真。如果当初不验证、直接把 4 条规则都上线，产品看起来功能齐全，实际上是「随机标红 26% 的 A 股」。

还有一个副产品：**把自己证伪的过程公开出来，反而增加了可信度。** 现在 README 里明确写着「净利现价比是反指标，已从产品中移除」，实验代码保留在 `scripts/` 目录，任何人都能复现。
